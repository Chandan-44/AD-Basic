🧠 The One-Sentence Summary of AD

"Active Directory is a database of objects (users, computers, groups) plus a set of rules and protocols that let those objects find each other, authenticate, and be authorized to access resources."

💡 Why Active Directory Exists

Before AD, every computer had its own list of users. Managing 500 computers and 500 employees meant creating 500 × 500 accounts. AD solved this.

❌ Without AD (Workgroup)

  • Every computer has its own user database
  • Same user must exist on every machine
  • Password changes repeated everywhere
  • No centralized control
  • No single sign-on
  • Scaling is painful

✅ With AD (Domain)

  • One central database
  • One account works everywhere
  • Changes propagate automatically
  • Centralized policy
  • Single sign-on
  • Scales to millions
📘 Simple Example

An admin at contoso.com with 200 employees and 300 computers.

Without AD: To give Alice access to 5 machines, you'd create her account 5 times.

With AD: You create Alice's account once. She can log in to any of the 300 machines.

🧩 Physical vs Logical Structure

AD has two parallel structures: a logical one (how you organize identity) and a physical one (how the network is laid out). They serve different purposes.

🧠 Logical Structure

Purpose: Organize identity and manage permissions

  • Forest
  • Domain
  • Organizational Unit (OU)
  • Objects (users, groups, computers)

Answers: "Who are you and what are you allowed to do?"

🌐 Physical Structure

Purpose: Control replication and network traffic

  • Site
  • Subnet
  • Site link
  • Bridgehead server

Answers: "Where are you and how do we reach you?"

📘 Why Both Matter

Logical view: Alice is in the Sales OU → she gets the Sales GPO.

Physical view: Alice is in the London site → she authenticates against the London DC.

Same user, two different lenses. Logical decides what applies. Physical decides who serves you.

🌲 Forest

What

The top-level container. A collection of one or more domains sharing a common schema, configuration, and global catalog.

Why

Defines the security boundary. Within a forest, domains trust each other automatically.

How

Identified by its root domain. All child domains share the schema.

Example

Contoso has contoso.com, emea.contoso.com, and asia.contoso.com — all one forest.

Forest Components Diagram

🌲 FOREST (root: contoso.com) │ ├── Shared Components (exist once): │ ├── 📐 Schema │ ├── ⚙️ Configuration Partition │ ├── 📚 Global Catalog │ ├── 👑 Schema Master FSMO │ └── 👑 Domain Naming Master FSMO │ └── Member Domains: ├── 🏛️ contoso.com ├── 🏛️ emea.contoso.com └── 🏛️ asia.contoso.com

Forest Component Cards

📐
Schema
Defines every object class and attribute. Shared across all domains.
⚙️
Configuration
Holds sites, services, and replication topology. Forest-wide.
📚
Global Catalog
Partial copy of all objects in every domain. Enables cross-domain search.
👑
Schema Master
FSMO role controlling schema changes.
👑
Domain Naming Master
FSMO role controlling adding/removing domains.
🧠 Mental Model

A forest is like a country. It shares one constitution (schema), one map (config), and one ID system (global catalog). Domains are like states.

🏛️ Domain

What

A logical grouping of users, computers, and objects sharing a common directory database and security policy.

Why

Domains let organizations delegate administration, apply different policies, and separate resources.

How

Each domain has its own DCs, user database, and security policies.

Example

contoso.com has its own DCs, users, and GPOs, separate from emea.contoso.com.

Domain Components Diagram

🏛️ DOMAIN (contoso.com) │ ├── Identity: │ ├── 👤 Users │ ├── 👥 Groups │ └── 💻 Computers │ ├── Infrastructure: │ ├── 🖥️ Domain Controllers │ ├── 🌐 DNS Zone │ └── ⏱️ Time Source │ ├── Policy: │ ├── 📝 Group Policy Objects │ └── 🔐 Security Policies │ └── Directory Partitions: ├── Domain Partition (users, groups, computers) ├── Configuration Partition (forest-wide) └── Schema Partition (forest-wide)

🖥️

🗄️

🌐
DNS Zone
AD-integrated DNS stores service records for DC discovery.
📝
GPOs
Group Policy Objects applied to OUs, sites, or the domain.
⏱️
Time Source
PDC Emulator provides accurate time for Kerberos.
🔐
Security Policies
Password policy, lockout policy, Kerberos policy.

📂 Organizational Units (OUs)

What

Containers inside a domain used to organize objects. Primary way to apply Group Policy and delegate administration.

Why

Large organizations need different rules for different groups. OUs allow fine-grained control.

How

OUs are hierarchical and can be nested. You can delegate control at the OU level.

Example

An Employees OU with sub-OUs for Sales, Engineering, and HR.

OU Tree Diagram

🏛️ contoso.com │ └── 📂 OU: Employees ├── 📂 OU: Sales │ ├── 👤 alice │ └── 👤 bob │ ├── 📂 OU: Engineering │ ├── 📂 OU: Backend │ │ └── 👤 carol │ └── 📂 OU: Frontend │ └── 👤 dave │ └── 📂 OU: HR └── 👤 eve
Important: OUs are not security boundaries. The security boundary is the forest. OUs are administrative containers.
📘 Why OUs Matter

Say you want a strict password policy for IT staff but a lenient one for Sales.

You put IT in one OU and Sales in another. Link different GPOs to each OU.

Result: same domain, different rules.

🌐 Sites

What

A physical network location defined by IP subnets. Helps AD route authentication to the nearest DC.

Why

Without sites, a user in Tokyo might authenticate against a DC in New York — slow and wasteful.

How

Each site is associated with subnets. Computers determine their site by IP.

Example

Site Tokyo has subnet 10.1.0.0/16. Site NewYork has 10.2.0.0/16.

Site Topology Diagram

🌍 Forest: contoso.com │ ├── 🌐 SITE: New York subnet 10.10.0.0/16 │ ├── 🖥️ NY-DC01 │ ├── 🖥️ NY-DC02 │ └── 💻 Workstations │ ├── 🌐 SITE: London subnet 10.20.0.0/16 │ ├── 🖥️ LON-DC01 │ └── 💻 Workstations │ └── 🌐 SITE: Singapore subnet 10.30.0.0/16 ├── 🖥️ SIN-DC01 └── 💻 Workstations SITE LINKS (replication): New York ⟷ London ⟷ Singapore
📘 Real-World Site Example

A multinational company has three offices:

  • New York — DC: NY-DC01
  • London — DC: LON-DC01
  • Singapore — DC: SIN-DC01

When Alice in London logs in, AD routes authentication to LON-DC01 — not to New York or Singapore.

🖥️ Domain Controller (DC)

What

A server that hosts a copy of the AD database and provides authentication, authorization, and directory services.

Why

AD needs authoritative sources. DCs are those sources.

How

DCs run AD DS and replicate with each other. Every DC has a full copy of the domain database.

Example

In a domain with 3 DCs, all 3 have the same data. If one fails, the others continue.

What a DC Does — Component Breakdown

🔐
Authentication
Verifies credentials via Kerberos or NTLM.
📖
Directory Services
Answers LDAP queries about objects.
🔄
Replication
Syncs directory data with other DCs.
🌐
DNS
Often hosts AD-integrated DNS.
⏱️
Time Source
Provides accurate time for Kerberos.
👑
FSMO Roles
Some DCs hold special roles.
🗄️
NTDS.dit
The AD database — all objects live here.
📁
SYSVOL
Shared folder with GPOs and logon scripts.
📘 What Happens When You Log In
  1. Workstation finds nearest DC (DNS + sites)
  2. Workstation sends authentication request
  3. DC verifies credentials
  4. DC issues a Kerberos TGT
  5. Workstation uses TGT to access resources

📚 Global Catalog

What

A partial, read-only copy of every object in every domain in the forest. Allows fast cross-domain lookups.

Why

Searching across all domains would be slow. The GC centralizes common attributes.

How

Any DC can be configured as a Global Catalog server. In single-domain forests, every DC is a GC.

Example

Searching for "Bob" in Outlook hits the GC — which knows Bob regardless of domain.

GC Lookup Flow

1
Client Query
Alice searches for "Bob" in the global address list.
2
GC Port Query (3268)
Query goes to the Global Catalog — a partial copy of every domain's objects.
3
Result Returned
GC returns matching objects with their common attributes — no need to query each domain.

What's in the GC vs What's Not

In Global Catalog ✅Not in Global Catalog ❌
Display nameFull password hashes (in domain partition only)
Email addressSome application-specific attributes
Group membershipsDetailed security descriptors
SIDComplete attribute set of every object
UPN, sAMAccountNameLarge binary attributes

👑 FSMO Roles

FSMO = Flexible Single Master Operations. Five special roles that must be held by specific DCs to avoid conflicts.

FSMO Role Hierarchy Diagram

🌲 FOREST-LEVEL ROLES (1 each per forest) │ ├── 👑 Schema Master │ → Controls changes to the AD schema │ └── 👑 Domain Naming Master → Controls adding/removing domains 🏛️ DOMAIN-LEVEL ROLES (1 each per domain) │ ├── 👑 RID Master │ → Allocates RID pools for SID generation │ ├── 👑 PDC Emulator │ → Password changes, time sync, legacy ops │ └── 👑 Infrastructure Master → Cross-domain object references

FSMO Component Cards

📐
Schema Master
Forest-wide. Only this DC can modify the schema (object classes, attributes).
🏛️
Domain Naming Master
Forest-wide. Only this DC can add/remove domains from the forest.
🔢
RID Master
Domain-wide. Allocates RID blocks to DCs so SIDs are unique.
⏱️
PDC Emulator
Domain-wide. Handles password changes, time sync, GPO editing.
🔄
Infrastructure Master
Domain-wide. Updates cross-domain references in multi-domain forests.
📘 Why FSMO Roles Exist

Imagine two DCs both try to add a new domain at the same time. Without a single master, they'd conflict.

So AD designates one DC as the Domain Naming Master. Only that DC can add domains — eliminating conflicts.

🗄️ AD Partitions

AD data is split into partitions. Each partition has its own replication scope. Understanding partitions helps you understand where data lives and how it replicates.

Partition Diagram

🗄️ AD PARTITIONS │ ├── 📘 Schema Partition │ Scope: Forest-wide │ Contains: Definitions of all object classes and attributes │ Replicates to: All DCs in every domain │ ├── ⚙️ Configuration Partition │ Scope: Forest-wide │ Contains: Sites, subnets, services, replication topology │ Replicates to: All DCs in every domain │ ├── 🏛️ Domain Partition │ Scope: One per domain │ Contains: Users, groups, computers, OUs (that domain only) │ Replicates to: All DCs in that domain only │ └── 📱 Application Partitions Scope: Custom (you choose) Contains: App-specific data (DNS zones, etc.) Replicates to: Only the DCs you specify

Partition Component Cards

📘
Schema Partition
The "dictionary" of AD. Defines what a User, Group, or Computer can have.
⚙️
Configuration Partition
The "map" of AD. Holds site and replication configuration.
🏛️
Domain Partition
The "content" — all users, groups, and computers in that domain.
📱
Application Partitions
Custom storage for apps (DNS zones often stored here).
📘 Why Partitions Matter

When you add a new user:

  • Only the Domain Partition changes (for that domain)
  • Only DCs in that domain replicate the change

When you modify the schema (rare):

  • The Schema Partition changes
  • Every DC in the entire forest replicates it

🧩 Objects

What

Any individual entry in AD — user, group, computer, printer, OU, GPO.

Why

AD is object-oriented. Everything is an object with attributes and permissions.

How

Each object is defined by a class and has attributes.

Example

CN=Alice,OU=Sales,DC=contoso,DC=com — one object.

Object Anatomy Diagram

🧩 OBJECT: Alice Smith │ ├── CLASS: user │ ├── ATTRIBUTES: │ ├── 🔤 sAMAccountName: alice │ ├── 📧 userPrincipalName: alice@contoso.com │ ├── 📛 displayName: Alice Smith │ ├── 📬 mail: alice.smith@contoso.com │ ├── 🔢 objectSid: S-1-5-21-...-1105 │ ├── 👥 memberOf: Sales, VPN-Users │ └── ⚙️ userAccountControl: NORMAL_ACCOUNT │ ├── PARENT: │ └── 📂 OU: Sales, OU: Employees, DC=contoso, DC=com │ └── ACL: ├── Allow: Domain Admins → GenericAll ├── Allow: HR-Team → GenericRead └── Allow: Helpdesk → ForceChangePassword

👤 Users

What

User objects represent people or services that need to authenticate. They hold credentials and attributes.

Why

Users are the primary identity in AD.

How

Each user has a username, UPN, password hash, group memberships, and many attributes.

Example

Alice has sAMAccountName: alice, UPN: alice@contoso.com, member of Sales.

User Object Diagram

👤 USER: alice │ ├── IDENTITY: │ ├── 🔤 sAMAccountName: alice │ ├── 📧 userPrincipalName: alice@contoso.com │ ├── 🔢 objectSid: S-1-5-21-...-1105 │ └── 📛 displayName: Alice Smith │ ├── CREDENTIALS: │ ├── 🔒 unicodePwd (NT hash + LM hash) │ ├── ⏰ pwdLastSet │ └── 📅 accountExpires │ ├── MEMBERSHIPS: │ ├── 👥 memberOf: CN=Sales,... │ ├── 👥 memberOf: CN=VPN-Users,... │ └── 👥 primaryGroupID: Domain Users │ ├── POLICY FLAGS (userAccountControl): │ ├── NORMAL_ACCOUNT (512) │ ├── DONT_EXPIRE_PASSWORD (65536) │ ├── ACCOUNTDISABLE (2) │ └── DONT_REQ_PREAUTH (4194304) │ └── OPTIONAL: ├── 🎯 servicePrincipalName (if service account) ├── 📞 telephoneNumber ├── 🏢 department └── 📍 officeLocation

Two Types of User Accounts

👤 Standard User

Represents a person. Has interactive logon rights.

Example: alice logs into her workstation.

⚙️ Service Account

Represents a service or application. Often has SPNs.

Example: svc_sql runs the SQL Server service.

👥 Groups

What

A container for users, computers, and other groups. Permissions are assigned to groups.

Why

Managing permissions one user at a time doesn't scale.

How

Groups have scope (Domain Local, Global, Universal) and type (Security, Distribution).

Example

Give the Sales group access to a shared folder. Add Alice → she has access.

Group Scope Diagram

👥 GROUP SCOPES │ ├── 🌍 GLOBAL GROUP │ ├── Contains: Users/computers from the same domain │ ├── Used in: Any domain in the forest │ └── Purpose: Organize users by role │ ├── 🏛️ DOMAIN LOCAL GROUP │ ├── Contains: Users, global groups, universal groups from any domain │ ├── Used in: Same domain only │ └── Purpose: Assign permissions to resources │ └── 🌐 UNIVERSAL GROUP ├── Contains: Users/groups from any domain in the forest ├── Used in: Any domain in the forest └── Purpose: Cross-domain role groups

AGDLP Strategy — Best Practice Diagram

👤 Account (Alice) ↓ 🌍 Global Group (Sales) ↓ 🏛️ Domain Local Group (Sales-Folder-Access) ↓ 📁 Permission (Read/Write on \\server\share) A = Accounts G = Global DL = Domain Local P = Permissions

Important Built-In Groups

🌲

📐

💻 Computers

What

A computer object represents a domain-joined machine. It has its own account and password.

Why

Machines need to authenticate, apply policies, and access resources.

How

When you join a machine, an account is created. Its password rotates every 30 days.

Example

PC-001 has account PC-001$ with its own password and SID.

Computer Object Diagram

💻 COMPUTER: PC-001$ │ ├── IDENTITY: │ ├── 🔤 sAMAccountName: PC-001$ │ ├── 🔢 objectSid: S-1-5-21-...-1234 │ ├── 📛 dNSHostName: PC-001.contoso.com │ └── 🌐 operatingSystem: Windows 11 Enterprise │ ├── CREDENTIALS: │ ├── 🔒 120-char random password │ └── ⏰ Password rotates every 30 days │ ├── OWNER: │ └── 👤 The user who joined the machine │ ├── LOCATION: │ └── 📂 CN=PC-001,OU=Workstations,DC=contoso,DC=com │ └── SPN (if server): └── 🎯 HOST/PC-001.contoso.com
📘 Why Computers Have Accounts

When PC-001 boots:

  1. It authenticates to the domain as PC-001$
  2. Downloads GPOs applied to its OU
  3. Accesses network resources granted to it

⚙️ Service Accounts

Service accounts are user accounts used by services rather than people. They often have elevated privileges and never change their password.

Service Account Types Diagram

⚙️ SERVICE ACCOUNT TYPES │ ├── 🔤 Traditional Service Account │ ├── A regular user account │ ├── Manual password management │ ├── Common: svc_sql, svc_backup, svc_web │ └── Downside: passwords often never rotated │ ├── 🖥️ Managed Service Account (MSA) │ ├── Password managed by AD │ ├── Tied to one computer │ └── Downside: can't be used across multiple servers │ ├── 🌐 Group Managed Service Account (gMSA) │ ├── Password managed by AD │ ├── Can be used across multiple servers │ ├── 240-character auto-rotated password │ └── Best practice for modern services │ └── 🤖 Virtual Account ├── Managed by Windows ├── No password at all ├── Used by built-in services (NT SERVICE\*) └── Not visible in AD

Service Account Attributes

AttributeMeaning
servicePrincipalNameIdentifies the service (e.g., MSSQLSvc/sql01:1433)
userAccountControlFlags like "password never expires"
msDS-ManagedPasswordFor gMSAs — auto-rotated password blob

📘 Why Service Accounts Matter

Service accounts often have:

  • Passwords that never change
  • Elevated privileges (local admin, domain admin in some cases)
  • SPNs that let them be identified via LDAP

Because they can't be easily disabled, they're attractive targets.

🔢 Security Identifiers (SIDs)

What

A unique, immutable identifier for every security principal.

Why

Names change; SIDs never do. Permissions use SIDs, not names.

How

Issued at object creation. Never reused.

Example

S-1-5-21-3623811015-3361044348-30300820-1105

SID Structure Diagram

🔢 SID: S-1-5-21-3623811015-3361044348-30300820-1105 │ ├── S → SID prefix (always S) │ ├── 1 → Revision number │ ├── 5 → Identifier Authority (5 = NT Authority) │ ├── 21 → NT Non-Volatile Authority │ ├── 3623811015-3361044348-30300820 │ → Domain identifier (3 sub-authorities) │ └── 1105 → RID (Relative ID — unique within domain)

📘 Why SIDs Matter More Than Names

Alice changes her last name from Smith to Jones. Her displayName changes, but her SID stays the same.

All her file permissions, group memberships, and access rights continue to work — because they're tied to her SID, not her name.

📐 Schema

What

The blueprint of AD — defines every object class and every attribute.

Why

To store data consistently, AD needs to know what kinds of objects exist and what they can contain.

How

Forest-wide. Changing it requires the Schema Master FSMO role.

Example

The User class has attributes like sAMAccountName, mail, memberOf.

Schema Structure Diagram

📐 SCHEMA COMPONENTS │ ├── 🧩 CLASSES (what can exist) │ ├── user │ ├── group │ ├── computer │ ├── organizationalUnit │ └── groupPolicyContainer │ ├── 📊 ATTRIBUTES (what can be stored) │ ├── sAMAccountName (string) │ ├── objectSid (binary) │ ├── memberOf (DN) │ ├── mail (string) │ └── userAccountControl (integer) │ └── 🔗 RELATIONSHIPS ├── user inherits from organizationalPerson ├── group inherits from top └── Each class has required + optional attributes
📘 Schema Extension in Action

When you install Microsoft Exchange, it extends the schema — adding hundreds of new attributes.

After the extension, User objects can have Exchange-specific attributes like msExchMailboxGuid.

Since the schema is forest-wide, the extension applies everywhere.

📋 Access Control Lists (ACLs)

An ACL is a list of rules that defines who can do what on an object.
What

A set of Access Control Entries (ACEs). Each ACE says "principal X can do action Y."

Why

AD needs to enforce granular permissions.

How

When you access an object, Windows evaluates the ACL.

Example

ACL on "Sales OU": Admins can modify, Helpdesk can create users, everyone can read.

ACL Anatomy Diagram

📋 ACL on object: CN=Alice,OU=Sales │ ├── ACE #1: │ ├── Principal: CONTOSO\Domain Admins │ ├── Type: Allow │ ├── Permission: GenericAll │ └── Inherited: No (explicit) │ ├── ACE #2: │ ├── Principal: CONTOSO\HR-Team │ ├── Type: Allow │ ├── Permission: GenericRead │ └── Inherited: Yes (from Employees OU) │ ├── ACE #3: │ ├── Principal: CONTOSO\Helpdesk │ ├── Type: Allow │ ├── Permission: ForceChangePassword (ExtendedRight) │ └── Inherited: Yes │ └── ACE #4: ├── Principal: CONTOSO\Bob ├── Type: Deny ├── Permission: WriteProperty (mail) └── Inherited: No (explicit)

🔐 DACL vs SACL

DACL

Discretionary ACL. Defines who is allowed or denied access.

SACL

System ACL. Defines what is audited.

DACL Example

"Allow Alice to read this file."

SACL Example

"Log every time someone tries to read this file."

DACL vs SACL Diagram

📋 OBJECT: SecretFile.txt │ ├── 🔐 DACL (Access Control) │ ├── Allow: Alice → Read │ ├── Allow: Admins → Full Control │ └── Deny: Bob → Read │ └── 📊 SACL (Auditing) ├── Success: Read (who successfully reads) ├── Failure: Read (who fails to read) └── Success: Write (who successfully writes)
📘 Both Work Together

A file might have:

  • DACL: Alice can read; Bob cannot
  • SACL: Every failed read attempt is logged

DACL decides access. SACL records what happened.

🌳 Inheritance

What

Child objects automatically receive permissions from their parent container.

Why

Without inheritance, you'd set permissions on every object individually.

How

By default, ACLs on an OU propagate to all objects within it.

Example

"Helpdesk can reset passwords" set on Employees OU → applies to all users inside.

Inheritance Flow Diagram

📂 OU: Employees ACL: Helpdesk → ForceChangePassword │ ├── 👤 alice ← inherits Helpdesk permission ├── 👤 bob ← inherits Helpdesk permission └── 📂 OU: Sales (inherits Employees OU permission too) │ ├── 👤 carol ← inherits from both OUs └── 👤 dave ← inherits from both OUs
📘 Why Inheritance Matters

An organization has 5,000 employees across 20 OUs.

Instead of setting "Helpdesk can reset passwords" 5,000 times, you set it once on the parent OU. All child users inherit it.

🎫 Access Tokens

When you log in, Windows creates an access token. That token contains your identity, group memberships, and privileges. Every action you take is checked against this token.

Access Token Structure Diagram

🎫 ACCESS TOKEN (created at logon) │ ├── 👤 User SID │ → S-1-5-21-...-1105 │ ├── 👥 Group SIDs │ → Sales, VPN-Users, Domain Users │ ├── ⚔️ Privileges │ → SeShutdownPrivilege, SeChangeNotifyPrivilege │ ├── 🔓 Integrity Level │ → Medium (or High if elevated) │ └── ⏰ Logon Session → Unique LUID for this session

Primary vs Impersonation Tokens

🎫
Primary Token
Assigned to a process at creation. Defines its default security context.
🎭
Impersonation Token
Assigned to a thread. Allows a thread to run as another user temporarily.
📘 Token in Action

You log in as Alice.

  • Your token contains Alice's SID + all her group SIDs
  • When you open a file, Windows checks the file's ACL against your token
  • If your token has a matching Allow ACE → access granted
  • If it has a matching Deny ACE → access denied

Your token is the single point of identity for everything you do.

🔑 Authentication Basics

Authentication = proving who you are. In AD, this is done via Kerberos (modern) or NTLM (legacy).
You provide credentials → DC verifies them → DC issues a ticket → You use the ticket

Authentication vs Authorization

🔑 Authentication

Question: Who are you?

Example: Login with username + password.

Handled by: DC (Kerberos/NTLM).

🔐 Authorization

Question: What can you do?

Example: Can you read this file?

Handled by: ACLs / access tokens.

🚪 The Logon Process (Step-by-Step)

What actually happens when you log in? Let's walk through it as a timeline.
1
You Type Credentials
You enter username and password on a domain-joined machine.
2
Find a DC (DNS + Sites)
Workstation queries DNS for _kerberos._tcp.contoso.com. AD returns the closest DC based on your site.
3
AS-REQ Sent
Workstation sends an Authentication Service Request (AS-REQ) to the DC. It contains the username and a timestamp encrypted with the password hash.
4
DC Verifies Credentials
The DC looks up your account, retrieves your password hash, and decrypts the timestamp. If it matches, credentials are valid.
5
AS-REP Returned with TGT
DC sends back an Authentication Service Reply (AS-REP) containing a TGT (Ticket Granting Ticket) and a session key.
6
TGT Cached in Memory
Workstation caches the TGT in LSASS memory. It will be used to request service tickets.
7
Access Token Created
Windows creates your access token: your SID, group SIDs, privileges, integrity level.
8
GPOs Applied
Workstation downloads GPOs from SYSVOL applied to your user and computer OUs.
9
Desktop Loads
You're now logged in. TGT in memory, token in LSASS, GPOs applied.
📘 Behind the Scenes — Why So Complex?

Every step exists for a reason:

  • DNS + Sites: So you don't authenticate to a DC on the other side of the world.
  • Timestamp encryption: So your password never crosses the network.
  • TGT: So you authenticate once, not for every resource.
  • Access token: So each action checks against your identity, not a global table.

🎟️ Kerberos

Kerberos is the default authentication protocol. It uses tickets instead of passwords, so credentials never cross the network.
What

A ticket-based authentication protocol using symmetric-key cryptography.

Why

Passwords should never cross the network. Kerberos solves this.

How

Three heads: Client, KDC, Service. Tickets prove identity.

Example

You log in — you get a TGT. You access a file share — you get a TGS for that share.

Kerberos Components Diagram

🎟️ KERBEROS COMPONENTS │ ├── 👤 CLIENT │ → You (or a service acting as you) │ ├── 🏛️ KDC (Key Distribution Center) │ → Runs on every Domain Controller │ ├── AS (Authentication Service) │ └── TGS (Ticket Granting Service) │ └── 🖥️ SERVICE → The resource you want to access (file share, SQL, web app)

Kerberos Authentication Flow Diagram

Step 1: You authenticate to the KDC (once) 👤 Client ──── AS-REQ ────→ 🏛️ KDC ←─── AS-REP ──── (contains TGT) Step 2: You request a service ticket 👤 Client ──── TGS-REQ ──→ 🏛️ KDC (uses TGT) ←─── TGS-REP ── (contains TGS for the service) Step 3: You access the service 👤 Client ──── AP-REQ ───→ 🖥️ Service (uses TGS) ←─── AP-REP ── (access granted)

Ticket Types

🎫
TGT
Ticket Granting Ticket. Proves you authenticated. Used to request service tickets. Valid ~10 hours.
🎟️
TGS
Ticket Granting Service. Proves you can access a specific service. Used to access that service.
📘 Kerberos Hotel Analogy

Think of Kerberos like a hotel:

  • Check-in desk (KDC): You show ID once, get a room key (TGT).
  • Gym access (Service Ticket): To enter the gym, use your room key to get a gym pass (TGS).
  • Gym door (Service): The gym reads your pass and lets you in — without knowing your ID or password.

Your password is never told to the gym, the restaurant, or the pool. Only check-in verified it.

🔒 NTLM

What

NT LAN Manager — the older Windows authentication protocol using challenge/response.

Why

Still used when Kerberos isn't available (by IP, non-domain, legacy apps).

How

Server sends a challenge; client responds with a hash of challenge + password hash.

Example

Accessing a workgroup share → NTLM used.

NTLM Authentication Flow Diagram

Step 1: Client sends username 👤 Client ─── Type 1 (Negotiate) ──→ 🖥️ Server Step 2: Server sends challenge 👤 Client ←── Type 2 (Challenge) ── 🖥️ Server Step 3: Client responds with encrypted challenge 👤 Client ─── Type 3 (Authenticate) ──→ 🖥️ Server (HMAC-MD5(password_hash, challenge)) Step 4: Server verifies (or forwards to DC) 🖥️ Server ── verifies locally or forwards to DC ──→ ✅

NTLM vs Kerberos Comparison

AspectNTLMKerberos
Password over networkNever (uses hash)Never
Mutual authNoYes
Delegation supportLimitedYes
Works by IPYesNo (needs hostname)
Works without DCYes (cached creds)No (needs KDC)
Modern preferenceFallbackDefault
Why modern environments prefer Kerberos: NTLM has known weaknesses. Many organizations now disable NTLM entirely.

📖 LDAP

What

Lightweight Directory Access Protocol — the language used to query and modify AD.

Why

Applications need a standard way to search, read, and write directory data.

How

You send LDAP queries to a DC. The DC responds with matching objects.

Example

Search for (&(objectClass=user)(department=Sales)) → returns all Sales users.

LDAP Distinguished Name (DN) Diagram

📖 DN: CN=Alice Smith,OU=Sales,OU=Employees,DC=contoso,DC=com │ ├── CN=Alice Smith → Common Name (the object) ├── OU=Sales → Parent OU ├── OU=Employees → Grandparent OU ├── DC=contoso → Domain component └── DC=com → Top-level domain Read right-to-left: com → contoso → Employees → Sales → Alice Smith

LDAP Query Components

SymbolMeaningExample
=Equals(cn=Alice)
&AND(&(dept=Sales)(title=Manager))
|OR(|(dept=Sales)(dept=Marketing))
!NOT(!(disabled=TRUE))
*Wildcard(cn=A*)
📘 Real LDAP Query Example

Find all users in Sales whose accounts are enabled:

LDAP
(&
    (objectClass=user)
    (department=Sales)
    (!(userAccountControl:1.2.840.113556.1.4.803:=2))
)

# Read as: users AND department=Sales AND NOT disabled

🔗 Trusts

A trust is a relationship between two domains or forests that lets users in one access resources in the other.
What

A logical link allowing authentication across domains/forests.

Why

Companies merge, partner, or have multiple domains. Trusts avoid duplicate accounts.

How

Trusts are directional (one-way or two-way) and transitive (or not).

Example

Users in emea.contoso.com access file shares in contoso.com — via automatic parent-child trust.

Trust Types Diagram

🔗 TRUST TYPES │ ├── 🌲 Parent-Child (Automatic) │ Direction: Two-way │ Transitive: Yes │ Example: contoso.com ⟷ emea.contoso.com │ ├── 🌳 Tree-Root (Automatic) │ Direction: Two-way │ Transitive: Yes │ Example: Between trees in the same forest │ ├── 🌐 External (Manual) │ Direction: One or two-way │ Transitive: No │ Example: contoso.com ⟷ partner.com │ ├── 🌍 Forest (Manual) │ Direction: One or two-way │ Transitive: Yes │ Example: contoso.com forest ⟷ fabrikam.com forest │ └── 🎭 Realm (Manual) Direction: One or two-way Transitive: No Example: Windows domain ⟷ Linux Kerberos realm

Trust Direction Diagram

One-way trust (contoso → fabrikam): 🏛️ contoso.com ─────→ 🏛️ fabrikam.com (users here can access resources there) Two-way trust (contoso ⟷ fabrikam): 🏛️ contoso.com ⟷ 🏛️ fabrikam.com (both directions — users can access each other's resources)
📘 Trust Example

Contoso acquires Fabrikam. Both have their own forests.

They create a two-way forest trust.

Result: Contoso users can access Fabrikam resources, and vice versa — but only if permissions are granted.

🎫 Delegation

Delegation lets a service act on behalf of a user. Instead of the user directly accessing backends, a frontend service does it for them.
What

A Kerberos feature allowing a service to impersonate a user when accessing another service.

Why

Multi-tier apps need to pass user identity from front-end to back-end.

How

Configured on the service account or computer account. Three types.

Example

A web app (frontend) queries SQL (backend) as the logged-in user.

Three Delegation Types Diagram

🎫 DELEGATION TYPES │ ├── ⚠️ Unconstrained Delegation │ ├── Service can impersonate user to ANY service │ ├── Caches user's TGT in memory │ ├── Historically dangerous │ └── Rarely used in modern environments │ ├── ✅ Constrained Delegation │ ├── Service can impersonate user to SPECIFIC services │ ├── Configured via msDS-AllowedToDelegateTo │ ├── Safer — limits scope │ └── Common in multi-tier apps │ └── 🛡️ Resource-Based Constrained Delegation (RBCD) ├── TARGET resource decides who can delegate to it ├── Configured via msDS-AllowedToActOnBehalfOfOtherIdentity ├── Most modern and granular └── Best practice

Delegation in Action Diagram

Scenario: Alice accesses a web app that reads from SQL 👤 Alice ─────→ 🌐 Web App ─────→ 🗄️ SQL Server (frontend) (backend) Without delegation: Web App can only access SQL as itself → SQL doesn't know it's Alice. With delegation: Web App impersonates Alice → SQL sees Alice's identity. Result: SQL applies Alice's permissions, not the web app's.
📘 Real-World Delegation Example

Scenario: A web app at web.contoso.com needs to read data from sql.contoso.com as the logged-in user.

  • Unconstrained: Web server can impersonate Alice to any service. Dangerous if compromised.
  • Constrained: Web server can only impersonate Alice to sql.contoso.com. Safer.
  • RBCD: The SQL server trusts web.contoso.com for delegation. Most granular.

📝 Group Policy Objects (GPOs)

GPOs are the central way to configure settings across the domain. Write once, apply everywhere.
What

A collection of settings defining how users and computers should be configured.

Why

Managing 1,000 machines individually is impossible.

How

You link a GPO to a Site, Domain, or OU. The settings apply under that scope.

Example

A GPO on the Workstations OU enforces screen lock after 5 minutes.

GPO Precedence Diagram

📝 GPO PRECEDENCE (last write wins) │ ├── 1. Local Policy │ (applies to the machine only) │ ├── 2. Site-linked GPOs │ (applies to all computers in the site) │ ├── 3. Domain-linked GPOs │ (applies to the whole domain) │ ├── 4. OU-linked GPOs (Parent) │ (applies to that OU and its children) │ └── 5. OU-linked GPOs (Child) (highest priority — applies last) Lower in the list = higher priority

What GPOs Can Configure

🔒
Security
Password policy, lockout, user rights, audit policy.
🖥️
Desktop
Wallpaper, Start menu, screensaver, taskbar.
📦
Software
Install, update, or remove applications.
🌐
Network
Firewall, proxy, mapped drives, VPN.
📜
Scripts
Login, logout, startup, shutdown scripts.
🔐
Certificates
Auto-enrollment, trusted roots.
📘 GPO in Action

Contoso wants:

  • All users: password minimum length of 12
  • IT staff: no USB drives
  • Kiosk machines: auto-login

Solution: three GPOs — one on the domain, one on the IT OU, one on the Kiosk OU.

📜 ADCS (Active Directory Certificate Services)

What

Microsoft's PKI. Issues digital certificates for authentication, encryption, and signing.

Why

Used everywhere — VPN, Wi-Fi (802.1X), smart cards, code signing, TLS.

How

A CA is deployed. It issues certificates based on templates.

Example

A user requests a VPN certificate. The CA issues it based on the "VPN User" template.

ADCS Hierarchy Diagram

📜 ADCS PKI HIERARCHY │ ├── 🌳 Root CA (Offline) │ → The trust anchor. Rarely online. │ ├── 🏛️ Issuing CA (Online) │ → Issues certificates to users/computers │ │ │ ├── Certificate Templates: │ │ ├── User │ │ ├── Computer │ │ ├── Web Server │ │ ├── VPN User │ │ └── Smart Card Logon │ │ │ └── Enrollment Methods: │ ├── Auto-enrollment (via GPO) │ ├── Manual (via web interface) │ └── API (via certreq, certipy) │ └── 📋 CRL (Certificate Revocation List) → List of revoked certificates

Certificate Template Components

👤
Subject
Who the certificate is for (user or computer).
🎯
Purpose (EKU)
What the certificate can be used for (client auth, server auth).
⏰
Validity Period
How long the certificate is valid.
👥
Enrollment Permissions
Who can request certificates from this template.
🔑
Key Usage
What cryptographic operations the key can perform.
📘 Real-World ADCS Example

Contoso deploys ADCS for:

  • Wi-Fi (802.1X): Users authenticate to corporate Wi-Fi with certificates.
  • VPN: Remote workers authenticate with certificates.
  • Internal HTTPS: Web servers get certificates from the internal CA.
  • Smart Cards: High-security accounts use certificate-based logon.

🌐 DNS in AD

AD depends on DNS. Every AD operation starts with a DNS lookup.
What

AD-integrated DNS — a DNS zone stored in AD that replicates and is secured by AD permissions.

Why

Clients must find DCs, Global Catalogs, and Kerberos services.

How

SRV records tell clients where the DCs are.

Example

Alice's login queries _kerberos._tcp.contoso.com to find the nearest KDC.

Key AD DNS Records Diagram

🌐 AD DNS SRV RECORDS │ ├── _ldap._tcp.dc._msdcs.contoso.com │ → Locate Domain Controllers (LDAP) │ ├── _kerberos._tcp.dc._msdcs.contoso.com │ → Locate Kerberos KDCs │ ├── _gc._tcp.contoso.com │ → Locate Global Catalog servers │ ├── _kpasswd._tcp.contoso.com │ → Locate Kerberos password servers │ └── _ldap._tcp.<site>._sites.dc._msdcs.contoso.com → Locate DCs in a specific site
📘 Why AD Needs DNS

Imagine logging in and the workstation doesn't know which DC to talk to → login fails.

AD relies on DNS to answer "where is the DC?" and "which DC is closest?" — every login, every resource access, every replication.

🔄 AD Replication

AD uses multi-master replication. Every DC has a full copy of the database, and changes on one DC propagate to all others.
What

The process by which DCs sync directory data with each other.

Why

Users can log in at any DC. Changes made on one must appear on all others.

How

DCs periodically replicate using RPC over IP (or SMTP in specific cases).

Example

Alice resets her password on DC01. Within seconds, all other DCs know.

Replication Components Diagram

🔄 REPLICATION COMPONENTS │ ├── 📊 Partition │ → Section of AD (Schema, Config, Domain) │ ├── 🔢 USN (Update Sequence Number) │ → Counter tracking changes on each DC │ ├── 📏 High-Water Mark │ → Highest USN seen from a partner │ ├── ⏱️ Intra-Site Replication │ → Every 15 seconds (same site) │ └── ⏱️ Inter-Site Replication → Scheduled (between sites)

Replication Flow Diagram

Intra-site (fast): 🖥️ DC01 ←── 15 sec ──→ 🖥️ DC02 🖥️ DC02 ←── 15 sec ──→ 🖥️ DC03 Inter-site (scheduled): 🌐 New York ←── scheduled ──→ 🌐 London 🖥️ DC01 🖥️ DC01 Compression and scheduling reduce WAN traffic
📘 Why Replication Matters

A domain has 5 DCs across 3 sites.

An admin in New York creates a new user on the New York DC.

Within seconds, all other DCs receive the update.

Result: The user can log in anywhere — no manual synchronization needed.

⏱️ Time Synchronization

Kerberos is time-sensitive. If clocks drift more than 5 minutes, authentication fails. This is why AD has a time hierarchy.
What

A strict time hierarchy that keeps all domain machines in sync.

Why

Kerberos tickets contain timestamps. If clocks differ too much, tickets are rejected.

How

The PDC Emulator is the authoritative time source. All DCs sync to it, and all member machines sync to their nearest DC.

Example

Workstation → closest DC → PDC Emulator → external NTP source.

Time Hierarchy Diagram

⏱️ AD TIME HIERARCHY │ ├── 🌍 External NTP Source │ (e.g., time.windows.com, pool.ntp.org) │ ├── 👑 PDC Emulator │ (the forest's authoritative time source) │ ├── 🖥️ Other DCs │ (sync to PDC Emulator) │ ├── 💻 Member Servers │ (sync to nearest DC) │ └── 💻 Workstations (sync to nearest DC)
5-minute rule: If time drift exceeds 5 minutes, Kerberos authentication fails. This is why time sync is critical.

📁 SYSVOL & FRS

SYSVOL is a shared folder on every DC that holds Group Policy Objects and logon scripts. It replicates between DCs using DFSR (or older FRS).
What

A shared folder (\\domain\SYSVOL) containing GPO files and scripts.

Why

Every DC needs the same GPOs so clients get consistent policy regardless of which DC they contact.

How

SYSVOL replicates via DFSR (modern) or FRS (legacy). Replication is separate from AD database replication.

Example

You edit a GPO. The change is written to SYSVOL on DC01 and replicates to all other DCs.

SYSVOL Structure Diagram

📁 \\contoso.com\SYSVOL\contoso.com\ │ ├── 📂 Policies\ │ ├── {GUID-1}\ │ │ ├── Machine\ (computer settings) │ │ └── User\ (user settings) │ └── {GUID-2}\ │ └── ... │ ├── 📂 scripts\ │ ├── logon.bat │ ├── startup.ps1 │ └── ... │ └── 📂 staging\ (temporary for DFSR)

FRS vs DFSR

FeatureFRS (Legacy)DFSR (Modern)
Full nameFile Replication ServiceDistributed File System Replication
EraWindows 2000–2008Windows 2008+
ReplicationFile-by-fileBlock-level (RDC)
EfficiencyLowerHigher (deltas only)

📘 Why SYSVOL Matters

When you log in:

  1. Your workstation contacts a DC
  2. The DC tells it which GPOs apply
  3. Your workstation reads the GPO files from SYSVOL
  4. Settings are applied

Because SYSVOL replicates, any DC can serve GPOs — no single point of failure.

❓ Common Questions

What's the difference between a forest and a domain?

A forest is the top-level security boundary — can contain multiple domains sharing a schema. A domain is a logical grouping of users and computers with its own database and DCs.

What's the difference between a global group and a domain local group?

Global groups contain users from their own domain and can be used anywhere in the forest. Domain Local groups contain users from anywhere but only assign permissions within their own domain.

Why does AD use DNS so heavily?

DNS is how clients find DCs, KDCs, and Global Catalogs. Without DNS, a workstation can't locate the services it needs.

What's the difference between Kerberos and NTLM?

Kerberos is ticket-based, more secure, supports mutual authentication. NTLM is challenge-response based and older. Modern environments prefer Kerberos.

What is a SID and why does it matter?

A SID is a unique, immutable identifier for every security principal. Permissions use SIDs, not names. Deleting and recreating a user gives them a new SID — old permissions don't carry over.

What's the difference between physical and logical structure?

Logical: forest, domain, OU — organizes identity and permissions. Physical: sites, subnets — controls network traffic and replication.

What are AD partitions?

AD data is split into partitions: Schema (forest-wide), Configuration (forest-wide), Domain (per domain), and Application (custom). Each has its own replication scope.

What's the PDC Emulator and why does time matter?

The PDC Emulator is one of the five FSMO roles. It's the authoritative time source for the domain. Kerberos requires clocks to be within 5 minutes, so time sync is critical.

What is SYSVOL?

SYSVOL is a shared folder on every DC that holds Group Policy Objects and logon scripts. It replicates between DCs using DFSR.

Why do service accounts matter?

Service accounts run services and often have elevated privileges. Traditional ones have passwords that never change. Modern best practice is gMSAs with auto-rotated passwords.

What's the difference between authentication and authorization?

Authentication: Proving who you are (login). Authorization: Deciding what you can do (ACLs).
